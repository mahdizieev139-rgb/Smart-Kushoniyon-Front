# ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ) — KUSHONIYON SMART MARKET

**Backend Development — Version 1.0**

> Этот документ — официальное техническое задание на backend-систему.
> Frontend (Next.js) разрабатывается отдельно и подключается к этому API.

---

## 1. Общая информация

- **Название проекта:** KUSHONIYON SMART MARKET
- **Тип продукта:** Digital Marketplace Platform / B2B SaaS
- **Локация:** рынок Кушониён, Душанбе, Таджикистан
- **Целевая аудитория:** покупатели строительного рынка, владельцы торговых точек, администрация рынка.

**Основная цель:** централизованная backend-система для управления магазинами, товарами,
продавцами, категориями, расположением торговых точек и администрацией рынка. Backend
предоставляет REST API для отдельного frontend-приложения на Next.js.

---

## 2. Технологические требования

**Обязательный стек:** Node.js, Express.js, TypeScript, PostgreSQL, Prisma ORM, Zod, JWT,
Argon2, Multer, S3-compatible Storage, Helmet, CORS, Rate Limiting, Vitest, Supertest.

- **Архитектура:** Modular Monolith
- **API Version:** v1
- **Base URL:** `/api/v1`

---

## 3. Роли пользователей

| Роль | Возможности |
|------|-------------|
| **CUSTOMER** | Просмотр магазинов, товаров, категорий; поиск; карта; контактная информация. |
| **SELLER** | Управление своим магазином и товарами; изображения; цены; статистика своего магазина. |
| **ADMIN** | Управление магазинами, продавцами, покупателями; подтверждение магазинов/товаров; категории; входы/секции; реклама; общая статистика. |
| **SUPER_ADMIN** | Полный доступ: администраторы, настройки, подписки, разрешения, журналы действий. |

## 4. Функциональные требования

### 4.1. Authentication
Регистрация, авторизация, выход, обновление токенов, получение текущего пользователя,
безопасное хранение паролей (Argon2), защита приватных маршрутов. Refresh tokens — ротация и отзыв.

### 4.2. Shop Management
CRUD: создание, список, по ID, обновление, удаление/архивирование, подтверждение, отклонение,
блокировка. **Статусы:** `PENDING`, `APPROVED`, `REJECTED`, `SUSPENDED`.
Поля: название, описание, телефон, изображения, ворота, секция, координаты (при наличии), статус.
Мультиязычность: `tj`, `ru`, `en`.

### 4.3. Product Management
Создание, редактирование, удаление, архивирование, просмотр, поиск, фильтрация, сортировка,
пагинация, подтверждение. Поля: название, описание, цена, валюта, категория, магазин,
изображения, статус доступности. Валюта по умолчанию — **TJS**. Цена — **Decimal**.
**Статусы:** `PENDING`, `APPROVED`, `REJECTED`, `ARCHIVED`.
Публичный API возвращает только `APPROVED` товары активных магазинов.

### 4.4. Category Management
Создание, редактирование, удаление/архивирование, вложенные категории, переводы на три языка.

### 4.5. Market Map Management
Управление воротами (Gates), секциями (Sections), расположением магазинов, координатами,
связями «секция — магазин». **Не использовать вымышленные реальные координаты** — предусмотреть
добавление точных координат после обследования рынка.

### 4.6. Search System
Поиск по: названию товара, названию магазина, категории, секции рынка.
Фильтры: категория, магазин, секция, минимальная/максимальная цена. Сортировка и пагинация.

### 4.7. Advertisement Management
Создание, редактирование, активация, приостановка, завершение, проверка периода действия,
привязка рекламы к магазину.

### 4.8. Subscription Management
Бизнес-модель: ежемесячная SaaS-подписка. Тарифы: **Basic 1 500 TJS/мес**, **Extended 2 500 TJS/мес**.
Реализовать планы, подписки, сумму, период оплаты, даты начала/окончания, историю изменений,
статус оплаты. На первом этапе — ручное подтверждение платежей. Не подключать непроверенные
платёжные сервисы.

### 4.9. Analytics
Общее количество магазинов, активных магазинов, товаров, продавцов, ожидающих подтверждения
товаров и магазинов; статистика по отдельным магазинам. Продавцы видят только свою статистику.

### 4.10. Audit Logs
Записывать важные административные операции (создание/изменение/подтверждение магазина и товара,
изменение подписки и прав доступа). **Не записывать пароли, токены и секреты.**

## 5. Требования к базе данных

PostgreSQL + Prisma. Обязательные модели: `User`, `Shop`, `ShopMember`, `ShopTranslation`,
`Product`, `ProductTranslation`, `ProductImage`, `Category`, `CategoryTranslation`, `Gate`,
`GateTranslation`, `Section`, `SectionTranslation`, `Advertisement`, `Subscription`,
`RefreshToken`/`Session`, `AuditLog`, `SystemSetting`.

Все основные модели: UUID, `createdAt`, `updatedAt`. Обеспечить: правильные связи, Foreign Keys,
Unique Constraints, индексы, Decimal для денег, транзакции, Soft Delete где необходимо.

---

## 6. Требования к API

Все маршруты начинаются с `/api/v1`.

**AUTH:** `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `POST /auth/refresh`, `GET /auth/me`

**SHOPS:** `GET /shops`, `GET /shops/:id`, `POST /shops`, `PATCH /shops/:id`, `DELETE /shops/:id`

**PRODUCTS:** `GET /products`, `GET /products/:id`, `POST /products`, `PATCH /products/:id`, `DELETE /products/:id`

**CATEGORIES:** `GET /categories`, `POST /categories`, `PATCH /categories/:id`, `DELETE /categories/:id`

**MARKET:** `GET /market-map`, `GET /gates`, `GET /sections`, `GET /sections/:id/shops`

**ADMIN:** `GET /admin/analytics`, `GET /admin/shops`, `GET /admin/products`,
`PATCH /admin/shops/:id/approve`, `PATCH /admin/shops/:id/reject`,
`PATCH /admin/products/:id/approve`, `PATCH /admin/products/:id/reject`

**SELLER:** `GET /seller/dashboard`, `GET /seller/shops`, `GET /seller/products`

Также: маршруты для рекламы, подписок, пользователей и управления изображениями.

## 7. Нефункциональные требования

**Производительность:** пагинация, индексы, отсутствие N+1, select нужных полей, оптимизация
поиска, транзакции для связанных операций.

**Безопасность:** Argon2, безопасные токены, RBAC, проверка владельца ресурса, Rate Limiting,
CORS Allowlist, Helmet, Zod-валидация, безопасная загрузка изображений, централизованная обработка
ошибок, защита секретов.

**Надёжность:** централизованное логирование, обработка ошибок PostgreSQL, проверка доступности БД,
Health Check endpoint, корректное завершение сервера, документирование резервного копирования.

---

## 8. Тестирование

Автотесты: регистрация, авторизация, logout, refresh token, CRUD магазина/товара, проверка прав
продавца, подтверждение администрацией, поиск, пагинация, фильтрация.
**Обязательно:** продавец не может изменять чужие магазины и товары. Отдельная тестовая БД.

## 11. Критерии приёмки

Backend готов, только если: (1) сервер запускается без ошибок; (2) PostgreSQL подключается;
(3) Prisma-схема валидна; (4) миграции выполняются; (5) все основные API работают; (6) авторизация
работает; (7) роли и права проверяются; (8) CRUD достаточно для MVP; (9) изображения загружаются
безопасно; (10) поиск и фильтрация работают; (11) тесты проходят; (12) TypeScript без ошибок;
(13) production build проходит; (14) документация готова; (15) frontend может подключиться к API.
